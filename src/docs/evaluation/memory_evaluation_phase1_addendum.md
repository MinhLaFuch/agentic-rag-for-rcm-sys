## 2. Behaviours to confirm (NOT auto-fixed)

1. **`check_profile_snapshot` is global.** It inspects the whole interactions frame, so with several users any
   future row of ANY user raises `LeakageError`. In practice the caller must pass an already-truncated
   snapshot, which makes the tool's own `timestamp <= as_of` filter effectively dead code. Probably by
   design ("assert the snapshot is clean"), but then the filter is untested by construction. The benchmark covers
   both: pre-truncated snapshot equals oracle-with-cutoff (cases 005-008), and an untruncated frame raises (015/016).
   Decide: keep as assertion, or scope the check to the queried user and let the filter do the work.
2. **Duplicate interactions (case 013).** `n_interactions` and `recent_items` count rows (a re-bought item appears twice
   in `recent_items`), while `top_categories` counts distinct items. Encoded as the expected contract; confirm it is intended.
3. **Unmapped `item_idx`** (not in `item2id`) is skipped for recent/price/categories but still counted in `n_interactions`.
4. `MEMORY_RECENT_ITEMS` is mirrored in the oracle (`DEFAULT_RECENT_N`); a test fails if config drifts.

## 3. Memory utility (Part B)

### 3.1 Important structural limitation
`score_trajectory` sets `task_success=None` for `personalized` requests when the planner has no `MemoryTool`.
Therefore:
- `personalized` (the kind that "isolates MemoryTool") **cannot be paired** against `planner`; the analyzer reports it as `no_pairs` with the unscored count.
- `constrained` and `cold_text` are ORACLE kinds, so in `memory_vs_no_memory` the only REALISTIC paired kind is `similar`.
A clean realistic memory ablation therefore needs either (a) scoring the no-memory planner on `personalized` (e.g. score it as
"could not personalize" instead of None), or (b) an explicit non-paired baseline such as `type1`/`baseline` – confounded by the planner, so label it as such.
This is a decision for the repo owner; no production scoring code was changed.

### 3.2 How to run (needs a real LLM; NOT executed in this patch)
```bash
# >= 3 independent runs, same seed/config so requests are identical; do NOT use --resume (it reuses trajectories => zero variance)
for i in 1 2 3; do
  python scripts/evaluation/run_agent_eval.py --agents planner,planner_memory --request-scope all \
      --per-segment 30 --tag memory_util_r$i
done
python -m package.evaluation.component.benchmarks.memory_utility \
    --dirs <experiments_dir>/agent_eval/exp_A <...>/exp_B <...>/exp_C --out-dir reports/memory_utility
```
Output: `memory_utility.json` + `.md`: per group (`realistic`, `realistic/<kind>`, `realistic/<kind>/<segment>`, same for `oracle`)
and per metric: n_pairs, unscored counts, means, diff with bootstrap CI over requests, run-to-run std, wins/losses/ties, verdict.

### 3.3 Interpretation rules
- Verdict is `inconclusive` unless n_pairs >= `--min-n` (20), runs >= 2 and the CI excludes 0. Cost metrics (tokens, latency) are "lower is better".
- ORACLE and realistic are never merged; there is no overall number.
- The old single-run ablation numbers: re-analysing them with this tool yields `inconclusive` + "single run" warning by construction.
  The old experiment directories were not part of the uploaded source, so they were **not** re-run here.
- Even a `memory_better` on `similar` says nothing about `personalized` and must not be reported as "memory improves quality".
